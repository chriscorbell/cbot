# Architecture

Dispatch is a Node server (`server/`) and a React web app (`web/`) that run on one machine together with every bot's screen, Chrome and Hermes gateway. In production that machine is a host of its own and the server a systemd service; in development it is the `dispatch-dev` container. Both are set up by `scripts/provision.sh`. `scripts/install.sh` puts a commit from GitHub on a host, and `scripts/deploy.sh` one from a checkout; both hand it to `scripts/release.sh` there. Hermes owns each bot's agent loop, history, memory, tools and model access. The server adds what Hermes does not have: the chat, one dressed screen per bot and a viewer for it, the app's own tools, routines and check-ins, the Library, group chats, and voice calls.

```text
browser
  │ HTTP + SSE (GET /api/events), VNC and voice calls over WebSocket, behind the session cookie
  ▼
server: Node, Hono, SQLite ──── displays.ts, desk.ts, vnc.ts ────────────┐
  │                        ▲                                             │
  │ POST /v1/runs          │ MCP: POST /mcp/<botId>, bearer token        ▼
  ▼                        │                                  X display per bot:
Hermes gateway, one per bot┘── browser (DevTools), terminal ──►  Xvnc, xfwm4, Chrome
  │
  ▼
model provider, SearXNG

server ── voice-relay.ts ──► speech container (Phonon, Parakeet, Nemotron, Silero VAD)
                     └────────► the bot's gateway (/v1/runs)
```

## Where each piece lives

| Piece | Where | What it does |
|---|---|---|
| API and realtime | `server/src/app.ts`, `routes*.ts`, `lib/hub.ts`, `lib/validate.ts` | JSON over HTTP, plus one Server-Sent Events stream (`GET /api/events`) carrying row updates, live state, roster, computer, routine and memory changes, and updates of Dispatch itself. `GET /api/search` (`search.ts`) finds messages in each bot's current chat and files in each Library by name, bounded per bot; the browser matches bot names itself. `app.ts` builds the app without starting anything; `index.ts` starts the process. Every request body is checked against a zod schema |
| HTTPS | `https.ts`, `httpsApi` in `routes-config.ts` | With `HTTPS=1` (the installer sets it), HTTPS on `PORT` with a certificate Dispatch signs itself, since browsers allow the microphone only over HTTPS and no public authority signs one for a local address. A certificate authority of the machine's own, name-constrained to exactly the names the certificate holds (localhost, the host name and `<host>.local`, 127.0.0.1 and the address the machine reaches the network from), signs it; both live in `DATA_DIR/https`, which a reset leaves alone. A new address gets a new authority and certificate, and a certificate near its end a new one from the same authority, checked at start and hourly. The port reads each connection's first byte: a TLS handshake gets HTTPS, plain HTTP from the machine itself is served as before (the health check, Tailscale Serve, the bots' MCP), and plain HTTP from elsewhere is redirected. `GET /api/https/certificate` (open) is the authority for a device to trust, offered in Settings > General when the page came over it |
| Updates | `updates.ts`, `UpdatePill` in `web/src/components/Sidebar.tsx`, `UpdatesSection` in `config/AppSettings.tsx` | Only on a machine the installer set up: one running a release under `/srv/dispatch/releases` and with `/etc/dispatch/source`, the repository and branch `install.sh` installed from (a `deploy.sh` host has none). A minute after starting and every six hours, the server asks GitHub's API for the branch's newest commit, and the sidebar offers it when it isn't the running one. Update (`POST /api/update`) runs the installer again, unattended, in a systemd unit of its own (`dispatch-update`) so it outlives the server; its `release.sh` restarts the service on the new release. While it runs, the server reads each step from the installer's log and sends `update` events. Each SSE `hello` names the running commit, and a page that saw an update start reloads when the commit changes. A failed unit leaves the old release running |
| Contracts | `types.ts`, `contract.ts`, `voice-protocol.ts` | What server and web share, imported by the web app as `@shared/*`: domain types and server events, HTTP responses, and a voice call's messages |
| Database | `db.ts`, `store.ts` | The whole schema with numbered migrations (`PRAGMA user_version`) and a record type per table. `store.ts` reads and writes bots and rows |
| Sign-in | `lib/auth.ts`, `routes-auth.ts` | One account on the owner's `users` row, which holds only a user name (also what the bots call the owner) and a scrypt hash of the password, both null on a fresh install. `GET /api/auth/me` says whether one exists; while none does, the web app shows the first-run form and `POST /api/auth/setup` creates it (once), with the setup code: a one-time code (`DATA_DIR/setup-code`, 0600, and the log) without which whoever reached Dispatch first on the network would make the account. The installer prints the address with it after `#setup=`, which the web app takes out of the address bar and keeps for the tab (`web/src/lib/setupCode.ts`), asking for it only when the page came without one; a wrong code counts as a wrong password, and making the account deletes it. A fresh install has no bot: after the account, `needsSetup` (the owner's `setup_at` is null) puts the setup wizard (`web/src/components/SetupWizard.tsx`) over the app. It makes the first bot with `POST /api/bots` when its name and look are chosen, so the bot's screen and gateway start while the user writes its label, About and instructions; connects a model through Settings > Providers or a sign-in with a code (`signin.ts`); and ends with `POST /api/setup/finish`, which has the bot greet the user if it has a model. The first bot a user makes is the primary one, and a bot made during setup holds its greeting until then (`bots.ts`). Accounts from before the wizard are past it. `POST /api/auth/login` gives a 30-day session cookie, `/logout` ends it, and `/password` changes the password and ends every other session. Every `/api` route needs the session except `/api/health`, those before one and the HTTPS certificate (`/api/https/certificate`); the web app's files and `/mcp/*` (bearer tokens) don't. A 401 carries no basic-auth challenge. A change to anything under `/api` (any method but GET, HEAD and OPTIONS), signing in included, and the screen and call WebSockets are refused with 403 when a browser sent them from another site's page, by its `Sec-Fetch-Site` or else an `Origin` that names another host (`crossSite`); the cookie is SameSite=Lax, which doesn't cover another port of the same address, and the API reads JSON whatever the Content-Type. The cookie is Secure when the browser came over HTTPS, its own or a proxy's (`X-Forwarded-Proto`). Every answer has a Content-Security-Policy that runs only the app's own scripts (and a blob: worklet and WebAssembly for calls), lets only the app frame its pages, and sends no referrer (`app.ts`). Ten wrong passwords from one address in 15 minutes shut it out for the rest of that window. `reset-account.ts` forgets the account from the command line and prints a new setup code |
| Turns | `agent/turns.ts`, `agent/transcript.ts`, `agent/live.ts`, `agent/prompt.ts` | One runner per bot runs its turns one at a time. A turn makes sure the bot's screen is ready, starts a Hermes run on the conversation's session (`POST /v1/runs`, with the app's instructions, which carry the bot's skills: up to 20,000 characters each and 50,000 in all), and a TurnTranscript turns the run's events into rows. `live.ts` holds what each bot is doing now |
| Engines | `engine.ts` | One Hermes home and gateway per bot: writes the home, starts or adopts the gateway, lists the providers and marks the ones that sign in with a code |
| Sign-ins | `signin.ts` | ChatGPT, Grok and Copilot sign in with the OAuth device flow: a link and a short code the user approves on any device, while the sign-in asks every few seconds. ChatGPT and Grok run `hermes auth add <provider>` for the bot's home in the background, with no terminal; the link and code are read from its output, and Hermes saves the sign-in to that home's `auth.json`. Copilot's is GitHub's device flow, run by the server with the github-copilot plugin's OAuth app; GitHub's token doesn't rotate, so it becomes the Copilot token in Settings > Providers for every bot. `POST /api/bots/:id/engine/login` and `POST /api/providers/copilot/login` answer with the link and code, `GET /api/signins/:id` says how it went, and `DELETE` cancels it. One runs per bot and one for Copilot; sign-ins live in memory |
| Provider settings | `settings.ts` | Model keys, subscription tokens, the self-hosted endpoint and the SearXNG address, one row each in `settings`, set in Settings > Providers (`GET`/`PUT /api/providers`). The browser learns only whether a secret is set and its last four characters |
| App tools | `mcp.ts`, `agent/tools.ts` | An MCP endpoint per bot (`POST /mcp/<botId>`). Tools: `save_file`, `create_routine`, `list_routines`, `update_routine`, `delete_routine`, `set_checkins`, `send_to_bot`, `create_group`, `post_to_group`, `show_weather`, `post_to_chat`, `ask_user`, `stay_silent`, `end_call`. Each tool's parameters are a zod schema, advertised as its JSON schema and checked on every call |
| Memory | `engine-memory.ts` | Reads `memories/USER.md` (what the bot knows about the user) and `memories/MEMORY.md` (its own notes) in the bot's Hermes home. The app shows the entries as "About you" and "Notes" and removes one when asked, holding the lock Hermes' memory tool writes under (an flock on `<file>.lock`, taken through util-linux `flock`) and replacing the file whole. Hermes reads both when a conversation starts, so a removal shows from the next conversation on. The server looks at the files every 3 seconds and sends a `memories` event when they change, so an open Memories tab shows what the bot saves |
| Displays | `displays.ts` | Starts and stops each bot's X display (Xvnc, a D-Bus session bus, xfwm4) and takes screenshots with ImageMagick |
| Screens | `computer.ts`, `desk.ts`, `box.ts`, `machine.ts`, `server/box/*` | Screen leases, dressing a screen as the bot's computer, the bot's Chrome, the home screen. `machine.ts` has the paths, ports and display numbers, which the box scripts' copies are tested against |
| Viewer | `vnc.ts` | WebSocket relay between noVNC in the browser and the display's VNC server. Watching drops the browser's input at the relay; Take control and Stop switch the open connection (`POST /api/bots/:id/screen/mode`, naming the connection the browser opened) rather than reconnecting |
| Scheduling | `routines.ts`, `proactive.ts` | Cron routines and check-ins for the primary bot. Each run is a turn; a routine run adds nothing to the chat beyond what the bot writes. A routine whose last run is still going or waiting skips a run, so one can't stack turns ahead of the user's messages. `DISPATCH_NO_SCHEDULER=1` turns both off |
| Group chats | `agent/rooms.ts` | A room is a bot row with a member list; posts go to its members' queues. It has no turns, skills, memory or routines of its own, so its settings show only General. Its About and Instructions go into each member's app instructions under the group's name |
| Voice | `voice.ts`, `voice-relay.ts`, `speech.ts`, `web/src/voice/*` | Voice calls through a relay on the speech service and the bot's own agent, voice previews, composer dictation, call records with summaries |
| Speech service | `speech/` (its own container) | Text-to-speech (Phonon 31M; ZONOS3-Mini in `zonos3/` is off, see `speech/README.md`), dictation and call transcripts (Parakeet Unified, Nemotron streaming, Silero VAD) over HTTP and a WebSocket at `SPEECH_URL`. `speech/README.md` has the API |
| UI | `web/src` | React and zustand: a sign-in screen, a rail of bot icons that opens into a full sidebar (names, previews, hidden bots), chat with a live "thinking" line, details panel (activity, computer, Library, an in-place look editor), a preview for Library files and chat attachments (`FilePreview.tsx`: pictures, PDFs, audio and video sent in place by `files/raw?inline=1` for the types in `INLINE_TYPES`, and text and Markdown read here, the first 512 KB of a long file through a byte range; HTML shows as source and SVG as a picture from a data: URL, so neither runs script at the app's address, even opened in a tab of its own), cards (approvals, questions, drafts, weather), voice call bar with captions, settings, viewer. On a phone: the sidebar as a drawer, dialogs as sheets, a hold for what a mouse does with hover and right-click (`lib/longPress.ts`), and the app kept as tall as what the keyboard leaves visible (`lib/viewport.ts`); `public/manifest.webmanifest` and the icons make it a home-screen app |

## Every bot is a Hermes home that Dispatch manages

Each bot, the primary one included, has a Hermes home at `DATA_DIR/engines/<botId>` and its own `hermes gateway run --no-supervise`, which Dispatch starts detached on 127.0.0.1 from port 8650 up. A gateway outlives a server restart, so a deploy leaves the bots working. The next server refreshes the home and adopts the gateway if its API key still works and the settings hash it started with still matches; otherwise it restarts it. The hash (`dispatch-settings` in the home) covers the config keys Dispatch owns (but the default model), the `.env` it writes, the Hermes pin that `provision.sh` records in `/opt/hermes/.dispatch-pin`, and the names of the app's MCP tools, which Hermes lists when it connects. A gateway whose bot's screen is down at that moment stays as it is, because a restart would only take its computer away.

A home is a Hermes root of its own rather than a profile under a shared root, because Hermes v0.23 folds every profile into one multiplexing gateway, which would mean one process and one `DISPLAY` for all bots. Hermes is installed once on the machine under `/opt/hermes`, and each home links `tools/`, `installs/` and `plugins/github-copilot` back to it. `/usr/local/bin/hermes` is a copy of the launcher, because Hermes rewrites the checkout's own launcher to point at whichever home ran it last.

`writeHome` builds or refreshes a home before each gateway start:

- `config.yaml` is created once. A new bot copies the primary bot's model, provider, auxiliary and fallback settings. After that Dispatch only rewrites the keys it owns, on every start: the toolsets for the API server and for Hermes cron, `agent.disabled_toolsets` (image generation, text to speech and Nous' connectors), the SearXNG search backend, the default model, its two endpoints under `providers:` (below), the terminal's working folder (the bot's Library), the bot's Chrome as `browser.cdp_url`, `mcp_servers.dispatch` with the bot's token, `timezone` from the server's `TZ`, and switches that keep Hermes off other cloud services (Nous guest tier, connectors, telemetry, update, catalog and plugin checks, speech recognition, language server downloads). The approval keys (`approvals.mode`, `approvals.deny`, `command_allowlist`) are written too, but kept out of the settings hash, since Hermes reads them again whenever the file changes (see Approvals below).
- The default model is the bot's chosen provider and model. Hermes resolves the default's credentials before it applies the provider a run asks for, so a default nobody has a key for would fail every run; Hermes' own cron jobs run on it too. With nothing chosen it is `deepseek-flash` when a DeepSeek key is set, unless a model was chosen in Hermes itself. Choosing a model rewrites it at once (`syncModel`); Hermes reads the file again, so it is kept out of the settings hash.
- `.env` holds the API server's key, port and host, the model credentials, `BROWSER_CDP_URL` and `SEARXNG_URL`. A credential set in Settings > Providers wins; one that isn't stays as the home has it (an older bot's own Copilot sign-in wrote its token there) or comes from the primary bot's home. Keys added by hand stay.
- `auth.json` holds the bot's own ChatGPT and Grok sign-ins (`signin.ts`), and a new bot starts without one. Copying the primary bot's would give two bots one refresh token, which a provider that rotates it on every refresh turns into a sign-out for whichever bot refreshes second. Claude has no sign-in: it runs on the token from `claude setup-token` in Settings > Providers (`CLAUDE_CODE_OAUTH_TOKEN`), which every bot shares, as it does Copilot's `COPILOT_GITHUB_TOKEN`. A Claude sign-in an older bot still has in `auth.json` comes first, and the token when that one fails.
- `SOUL.md` is the persona, written from the bot's name, role and description.

The gateway's environment has only `PATH`, `HOME`, `USER`, `LANG`, `TZ`, `HERMES_HOME`, its lock folder, `BH_HOME` and the bot's `DISPLAY`, none of the server's secrets. `BH_HOME` gives each gateway its own browser helper; with the default every bot would drive the same browser.

The Engine section lists the providers in `PROVIDERS` (`engine.ts`), under their Hermes ids:

| Provider | Hermes id | Credential |
|---|---|---|
| Claude subscription | `anthropic` | `CLAUDE_CODE_OAUTH_TOKEN` for every bot, from `claude setup-token` |
| ChatGPT subscription | `openai-codex` | Sign-in with a code, per bot |
| Grok subscription | `xai-oauth` | Sign-in with a code, per bot |
| GitHub Copilot | `copilot` | `COPILOT_GITHUB_TOKEN` for every bot, from a GitHub sign-in with a code or pasted |
| Anthropic API | `anthropic-api` | `DISPATCH_ANTHROPIC_API_KEY`, through an endpoint Dispatch declares |
| OpenAI API | `openai-api` | `OPENAI_API_KEY` |
| Google Gemini | `gemini` | `GEMINI_API_KEY` |
| xAI API | `xai` | `XAI_API_KEY` |
| OpenRouter | `openrouter` | `OPENROUTER_API_KEY` |
| DeepSeek | `deepseek` | `DEEPSEEK_API_KEY` |
| Self-hosted | `self-hosted` | `DISPATCH_SELF_HOSTED_API_KEY`, if set, through an endpoint Dispatch declares |

The two endpoints are Hermes named custom providers in `config.yaml`'s `providers:`, present while their key or address is set. `anthropic-api` points at `https://api.anthropic.com` with the `anthropic_messages` transport. It exists because Hermes would use an `ANTHROPIC_API_KEY` for the `anthropic` provider too, ahead of a bot's Claude sign-in, which would move every subscription bot onto paid API use. `self-hosted` points at the address set in Settings, an OpenAI-compatible server. Hermes asks only the current provider's endpoint for its models, so Dispatch asks both endpoints itself (`endpointModels`, kept for a minute) and offers what they list.

Whether a provider is connected comes from Hermes' own `/api/model/options`. Signing in opens a terminal on the bot's screen that runs `hermes auth add <provider>` with `BROWSER` set to the bot's Chrome, and the user finishes it through the viewer.

A gateway loads its home's `.env` into its environment when it starts, and falls back to that copy when the file loses a key, so a change in Settings > Providers restarts every gateway: an idle one at once, a busy one before its next run (`refreshEngines`; `engineFor` waits for it). A secret taken out of Settings also leaves every home that still holds that same value, so a bot's own sign-in stays. The first start of this version copies the provider variables still in the server's environment into `settings` once (`importEnvironment`).

## Each bot has its own screen and Chrome

`displays.ts` runs one X display per bot: `:99` for the primary bot and the lowest free number from `:100` for the others. Each display is TigerVNC's `Xvnc` at 1440x900 with its VNC server on 127.0.0.1:5900+N and no VNC password, a D-Bus session bus, and `xfwm4 --compositor=off`. Every piece carries `DISPATCH_DISPLAY=<n>` in its environment, which is how a running display is found again. A display stops only when its bot is deleted. A lease in the `screens` table outlives the server, and on start the server brings back every leased screen with its dressing.

`desk.ts` makes a screen look like the bot's own computer. It installs the scripts in `server/box/` under `/opt/dispatch` (again whenever they change) and calls `dispatch-screen.py` with one short command per action. One-time setup starts the home-screen server (`dispatch-home.py` on 127.0.0.1:7391, which serves each Chrome its own bot's page, and only to requests that name it by that address, so a web page that points its own name at 127.0.0.1 gets nothing) and a Chrome policy that installs the home-screen extension; the extension's signing key stays in `/root/dispatch/home-extension.pem`, so its id survives a rebuilt dev container. Dressing a screen sets a wallpaper in the bot's colour, a dock, a light theme, and starts Chrome with the profile `/root/dispatch/profiles/<botId>`, DevTools on port 9200+N, maximized on the home screen. A stamp on disk records what was applied, so a repeat call costs one shell command.

Before each turn, `screenForWork` leases and dresses the screen and checks that its Chrome answers on DevTools, dressing it again if not, so the agent finds its browser instead of starting one of its own. A screen that cannot be readied is logged and the turn goes on without it. Hermes' browser tool uses that Chrome through `browser.cdp_url`, so everything it does shows in the viewer.

The viewer relay (`vnc.ts`) checks the browser's session cookie, does the RFB handshake with Xvnc itself, then offers the browser an unauthenticated RFB session. In watch mode it drops key, pointer and clipboard messages on the server. When the user hands the screen back after taking control, the bot's next turn starts with a note to look at the screen before relying on it. Resetting a screen closes every window and brings Chrome back to the home screen; logins stay.

Hermes can also run a private "Bot Desktop" for a home. While it runs, that agent's computer-use tool acts there and not on the screen the app shows, so the Engine section reports it and offers to stop it.

## The transcript is a list of rows

A conversation is an append-mostly list of rows: `seq` (position), `updatedSeq` (a per-bot revision counter), `kind` and a JSON `body`. A streaming reply is the same row rewritten with a higher `updatedSeq`, so clients upsert by `seq`. A per-bot `generation` counter starts a new conversation ("New chat"), and with it a new Hermes session (`dispatch-<botId>-g<generation>`). Rows of earlier generations stay in the database, unseen, and a row is addressed by bot, generation and seq (`RowRef` in `store.ts`). Work that outlives a request, such as a turn, its app tools or the sweep of abandoned voice calls, writes through a `Conversation`: once the user starts a new chat its appends are dropped and its updates land on its own rows, so nothing of an old chat shows in the new one. A call's end record is written by the request the browser sends at hang-up, into the bot's current chat.

Row kinds: `message` (from the user, the bot, another bot or a voice call; a `note` is the bot thinking aloud, kept but hidden), `tool-call` (an activity line and a step in the collapsible list), `card` (approval, question, weather, and draft cards in older chats), `event` and `notice`. A question card goes from pending to answered once.

`agent/transcript.ts` decides what a turn's text becomes. Text is held until it is clear whether a tool call follows it: then it is a note, and the status line shows its first sentence; otherwise it is a message. A turn that wrote only notes answers with its last one. `test/turn.test.ts` replays scripted Hermes runs to pin this.

What a bot is doing now (`agent/live.ts`) is idle or running, with an activity, a start time and a caption from its reasoning. It is kept in memory and sent on the event stream.

A bot's runner (`agent/turns.ts`) runs one turn at a time. Stop ends the running turn and asks Hermes to stop its run, and lets queued ones run; New chat and deleting the bot also drop the queue, and a turn queued before a New chat is skipped.

A turn is a Hermes run (`POST /v1/runs`, then `GET /v1/runs/<id>/events`) on the conversation's session. A run's events carry text deltas, commentary, tool starts and ends with an error flag, reasoning, approval prompts and the final answer; unlike the Responses stream used before, they carry no tool arguments or full results, so a tool row has a status but rarely a reason, and an app tool's arguments come from its MCP call. Chats from before runs kept their history in a Responses conversation, which a run can't continue: the first run of such a chat (its session doesn't exist yet and the bot has answered in it) starts with a recap of the messages the chat shows. Right after a gateway starts (or this server does), the bot's first run goes alone until Hermes begins answering it, at most 30 s (`runSlot` in `engine.ts`): Hermes loads a provider's SDK on first use without a lock, and a chat turn and a voice reply that load the Anthropic SDK at the same moment could fail one of them.

The model's own history is Hermes' business; the app keeps only what it shows.

## Hermes asks before risky actions, in the chat

Settings > Permissions sets how every bot's Hermes asks before an action it flags as risky, such as a command that matches its dangerous patterns or a write to `~/.ssh/config`: Off (it never asks), Smart (Hermes' auxiliary model clears low-risk actions and asks about the rest) or Ask (`manual`: it always asks). The choice is `users.approval_mode`: a new owner starts on Smart (`ensureOwner`), and accounts from before keep the column's old default, Off. `engine.ts` writes it into every bot's `config.yaml` as `approvals.mode`, with `approvals.deny` ("Never Allow": glob patterns of terminal commands Hermes refuses in every mode, from `users.approval_deny`) and `command_allowlist` ("Allow without Asking"). Hermes reads these again when the file changes, so a change applies to running gateways at once.

When Hermes asks, the run sends `approval.request` and waits, for up to its 5-minute timeout. A chat turn or a voice call hands the prompt to `agent/approvals.ts`, which adds an approval card to the bot's chat and a row in `approvals`, and the tool's row waits with it. The card shows Hermes' description and the command, with the answers Hermes offers: Allow (`once`), Always allow and Don't allow. The answer goes to `POST /v1/runs/<id>/approval` with Hermes' prompt id and the run's execution generation, and the run carries on. Hermes saves an "Always allow" into the asking bot's `command_allowlist`; Dispatch then gives every bot the union, and removing an entry in Settings takes it from all of them. A prompt that ends without an answer (Hermes' timeout, Stop, a call hanging up) expires its card: after each later event of a run with an open prompt, Dispatch checks the run's `pending_controls`, and the run's end expires whatever is left.

Pending prompts live in memory beside their runs, so one left by a process that stopped expires at startup. Hermes' hard blocks, such as credential files, apply in every mode, and the app's own MCP tools never ask. Draft cards and the `policies` table are from an earlier version that asked before tools itself; nothing creates or reads them.

## Bots work together through the app

- `send_to_bot` puts a message from one bot into another bot's queue, and the reply comes back the same way. After three hops between bots the tool refuses and tells the bot to answer the user.
- A group chat is a bot row with `kind='room'` and a member list. A user message goes to the @mentioned members, or to all of them, at most three; each one answers with `post_to_group` or stays silent. Files attached in a group are uploaded to the group's own folder (`files/<roomId>/uploads`), which its chat shows them from. Sending the message copies them into every member's Library under `uploads/` (`library.ts`, numbered when the name is taken), and the members asked to answer are told where their copies are. A group has no voice calls. The group's About and Instructions reach its members through their app instructions (`agent/prompt.ts`), not through each group message, so they don't pile up in every member's history; its label is only shown in the app.
- For work inside one task, Hermes' own delegation (the `delegation` toolset) is used.
- The primary bot gets check-ins at the times set with `set_checkins` and sends one short message or calls `stay_silent`. A check-in is skipped when the user sent a message in the last 20 minutes.

## A voice call is the bot's own agent behind a speech relay

Each thing the user says on a call is a turn of the bot's Hermes agent, on the bot's model and with all its tools. `POST /api/voice/session` writes the call's start row, wakes the bot's gateway and screen, fixes the call's instructions (the app's usual instructions, then a call section: talk instead of writing and post what is better read with `post_to_chat`, the local time, what the bot is doing in its text chat, and the last 14 chat messages), picks a greeting, and returns the relay's path, `/api/voice/relay/<callId>`. It answers 503 when the speech service is down. The browser opens the path on its own origin with `ws:` or `wss:` to match the page. Like the viewer, the relay accepts the session cookie, and it takes one socket per call.

The browser (`web/src/voice/call.ts`) speaks a subset of OpenAI's Realtime events, and the relay (`voice-relay.ts`) answers it:

- The microphone's PCM (16-bit mono, 24 kHz, 40 ms frames, resampled in an AudioWorklet from the context's rate) goes to the speech service's recognition socket. The call cancels the bot's echo itself, as a native call app does: browsers' own cancellers let the bot's voice reach the microphone at −8 to −12 dB with desk speakers in Safari and Firefox, whether it played from an AudioContext or through WebRTC, and the recognizer heard it as the user talking over the bot. So the microphone is opened with the browser's echo cancellation, noise suppression and gain control off, and WebRTC's AEC3, compiled to WebAssembly (`web/src/voice/aec.ts`, `@ennuicastr/webrtcaec3.js`, loaded when a call starts), subtracts what the call plays: the capture worklet takes the call's sound as a second input, on the same AudioContext clock as the microphone, and AEC3 gives the microphone back at 24 kHz about 10 ms later. When Firefox can't capture the microphone in the call's context (another rate), the call moves its playback to the microphone's context before it connects. If AEC3 can't load or start, the browser's canceller is used, and the bot plays through WebRTC (below). After the canceller, while the bot is audible, each frame goes through an echo gate (`web/src/voice/echo.ts`) for what is left. The gate sends a frame only if it is more than 2.5 times as loud as the bot's voice at the microphone, and silence in its place otherwise; a frame that goes out keeps the gate open for 480 ms, and once the relay pauses the bot everything goes out again. How loud the bot is at the microphone is learned during the call, as the ratio of microphone to output energy while the bot makes sound (from the player's AnalyserNode), each frame counted at most as loud as the gate's limit so that talking over the bot barely moves it. The call's end sends what the canceller and the gate did, and the server logs it with the browser's name. With AEC3 it also sends the call second by second while the bot was audible (`web/src/voice/echo-log.ts`, logged on a second line): what played, what the microphone heard and what AEC3 left, the echo's delay (the lag at which the microphone's 1 ms envelope best matches what played), render quanta that brought no microphone audio, and the context's output latency, so a moment where the bot's voice got through shows whether the room got louder, the delay moved or the microphone dropped audio. Firefox won't connect a microphone to a context at another sample rate (Mozilla bug 1674892), so then the browser captures in a context of its own at a rate it accepts; a microphone that sends no frames for three seconds ends the call with a message. Its `speech_started` and `speech_stopped` become `input_audio_buffer.speech_started` and `.speech_stopped`, each `partial` becomes `conversation.item.input_audio_transcription.updated` with the transcript so far, `final` becomes `.completed`, and `speech_dropped` becomes `conversation.item.deleted`. Muting sends `reset`.
- The browser's first `response.create` gets the canned greeting, spoken at once. The first turn is told what it was.
- Each final transcript with words in it starts a Hermes run (`POST /v1/runs`) on the call's own session, `dispatch-<botId>-<callId>`, with the call's instructions, the bot's model and provider and its reasoning effort. The relay follows the run's events (`GET /v1/runs/<id>/events`). Runs can be stopped and steered and carry Hermes' approval prompts, which is why chat turns use them too.
- `message.delta` text is cut into sentences, and the speech service speaks them one after another in the bot's voice and speed. Text before a tool call is spoken when the tool starts. The audio goes out as `response.output_audio.delta`, each sentence as a transcript delta, between `response.created` and `response.done`.
- With AEC3 the browser plays the bot's audio and the thinking loop straight from the AudioContext. With the browser's canceller instead, it plays them through a WebRTC connection between two peer connections in the page, from an audio element (`CallOutput` in `web/src/voice/audio.ts`), since a browser's canceller subtracts only the audio it knows is the far end of a call (Chrome's does then; Safari's didn't). The connection adds about 40 ms. If it doesn't connect within three seconds, or drops mid-call, the call plays straight from the AudioContext; the server's log of the call's end says which way it played.
- Each `tool.started` sends `dispatch.activity` with its label ("Running commands") for the call bar. While a reply is in progress and no audio is playing, the browser plays a quiet loop made with Web Audio (`ThinkingLoop` in `audio.ts`), after 350 ms of quiet; it fades out when audio starts.
- `end_call` is one of the app's MCP tools. When the run starts it, the relay speaks what came before, sends `dispatch.hangup` and stops the run; the browser hangs up once its audio has played.
- A Hermes approval prompt (`approval.request`) becomes a card in the bot's chat, as in a text turn, and the call bar says "Waiting for you in the chat" until it is answered there. The reply waits meanwhile, for up to Hermes' timeout.

The speech service ends an utterance after 500 ms of silence. When the user starts talking, the browser pauses the bot's audio, keeping what it hasn't played, and the relay starts no new sentence. The final transcript decides what that was, and the relay tells the browser with `dispatch.playback`. With no words (a cough, a noise, the bot's own voice coming back through the microphone, or the microphone muted mid-utterance) the bot plays on from where it paused. Over the bot's speech, a final that names the streaming model doesn't count as words either: Parakeet found none in it, and the stream's guess at a short sound is how noise had become "That's" and cut the bot off. Neither does a final whose words are, in order, the end of what the bot was saying (the sentence playing at the pause and the one before it, one word in four allowed to differ): with speakers and a microphone in the same room, some of the bot's voice gets past the echo canceller and the recognizer writes it down. Nor does a final of at most three words that only acknowledge the bot ("yeah", "mm-hmm", "okay", "right"; `isAck`): that isn't the user taking a turn, and a scrap of the bot's voice that got past the canceller had come out as "Yeah." and cut it off. It does count when the pause came in the last sentence of a finished reply and that sentence asks something, since then "yeah" is an answer. With words, the browser drops the audio it holds, and:

- If a tool call is running, they go to the run with `POST /v1/runs/<id>/steer`. Hermes hands them to the agent when the tool batch ends, before its next model call, and the same turn answers. A steer sent while the model is writing could miss that point and land after the turn, which is why only a running tool gets one.
- Otherwise the run is stopped (`POST /v1/runs/<id>/stop`, about 0.15 s) and a new one answers. A stopped run keeps the user's words and its finished tool calls in the session's history; a run stopped while still queued doesn't, so its words go into the new run's input.
- The relay mirrors the browser player's schedule. When the user talks over a reply, the next turn starts with a note saying how much of it they heard, because the agent's history keeps everything it wrote.

When the call ends, a run still going is stopped. The browser posts its transcript to `POST /api/voice/end`, which writes the end row. The bot's own agent then adds a title and a one-sentence summary to that row: one short Hermes run, on the model the call used, on a session of its own beside the call's (`<call session>-summary`), given the transcript. Hermes holds the bot's model access, so any provider works.

### A call and the text chat tell each other what they missed

A call's conversation in Hermes is apart from the chat's, so that a call answers at once while a chat turn works, and its turns don't carry the chat's whole history. The chat's rows are the record of both, and `agent/catchup.ts` tells each conversation the rows it did not write, as a bracketed note at the start of a run's input (the instructions, and the prompt cache behind them, stay the same):

- Each run on a call starts with what is new in the text chat since the call's last run: messages typed there, the bot's finished replies there, questions waiting for an answer, the app's notices. The call follows the bot's row revision rather than seq, because a reply is rewritten as it streams and a note can become a turn's answer at its end; a row is told once, when it is finished. A run stopped before Hermes started it asks again with its notes as well as its words.
- A chat turn starts with the calls that ended since the chat's last turn, each with its transcript, and what a call posted in the chat. `bots.told_seq` is how far into the current chat its agent has been told; a turn moves it once Hermes has accepted the request, so a turn that never reached Hermes leaves the news for the next one, and New chat starts it again at 0.
- `post_to_chat` puts a bot message in the chat, for what is better read than heard. An app tool call that no chat turn claimed, made while the bot is on a call (`liveCallOf` in `voice.ts`), is the call's, and the message carries the call's id: the call isn't told its own posts, and the chat's next turn is.

A call's tool calls don't appear as steps in the text chat (what it posts with `post_to_chat` does), and a call can run while a chat turn runs. Both share the bot's screen and Chrome. An app tool call reports its outcome into a chat turn, or ends it (`ask_user`, `stay_silent`), only if it claimed one of that turn's tool rows (`claimToolRow` in `agent/turns.ts`). The MCP request names the bot but not the conversation, so a call's tool use can still claim a chat turn's row when both use the same tool at the same moment.

A bot stores a voice id and a speed (`speech.ts`): one of Phonon's 37 voices, which the picker groups as American, British and Characters. ZONOS3-Mini's voices replaced them for a day; a bot still storing one (`zonos3-…`) reads as its nearest Phonon voice (the same gender and accent, Hugh for the Irish Cillian, the closest character otherwise), and the stored id is left alone, so turning ZONOS3 back on brings it back. Any other voice the speech service doesn't list reads as its default, `harper`, and a speed is clamped to 0.86 to 1.27, on every read and write. New bots get one of six clear, even voices, picked by id. Phonon drops dashes, so the speech service turns them into commas and stops first (`speech/app/text.py`). Voice previews stream the speech service's PCM through `POST /api/voice/preview`, and composer dictation sends the recording through `POST /api/voice/stt` to the speech service's Parakeet transcription.

On the dev machine, with the primary bot on `deepseek-flash`, the answer's first audio came 2.4 s and 2.9 s after the end of the user's speech at the medians of two five-question runs (2.3 to 3.8 s): about 0.7 s for the final transcript, and most of the rest Hermes and the model before the first token. A steered question during an 8-second `sleep` was answered in the same turn. Speech over a reply pauses it 0.21 to 0.29 s after the user starts talking.

## Data lives in two places

| Production | Dev container | Holds |
|---|---|---|
| `/var/lib/dispatch` (`DATA_DIR`) | volume `data` at `/data` | `dispatch.db` (SQLite in WAL mode, schema in `db.ts`: the user and sessions, bots, rows, approvals and policies, routines, skills, screen leases, check-ins; older databases also keep tables nothing reads), `secret` (signs the MCP tokens), `auth-fingerprint`, `setup-code` while no account exists, and `engines/<botId>`, each bot's Hermes home with its gateway log |
| `/root/dispatch` | volume `root` at `/root` | `profiles/<botId>` (Chrome profiles), `files/<botId>` (the Library, also the bot's working folder), the home-screen extension key |

Hermes (`/opt/hermes`) and the packages come from `provision.sh`, the box scripts are copied into `/opt/dispatch`, and the display and Chrome logs go to `/var/log/dispatch`. On the host all of it stays, along with whatever the bots install; in the dev container only the volumes survive a rebuild. Deleting a bot (`deleteBot` in `bots.ts`) removes its row first, so requests about it fail from then on, then stops its turns, gateway and display, deletes its home, Chrome profile and Library folder, and frees its screen lease last. A deleted group only has its folder of attached files to remove.

Settings > General > Reset Dispatch (`reset.ts`, `POST /api/reset`, behind two confirmations) deletes every bot that way, then erases the rest of both places: every Chrome profile and Library folder, and in `DATA_DIR` the database with any old copies, `secret`, `auth-fingerprint`, `setup-code` and `engines/`. Then the server writes the new install's setup code, which the reply already gave the browser, and exits, and systemd (`Restart=always`) or the container's restart policy starts it again as a fresh install, with no account; the web app waits for that and reloads into the first-run form with the code filled in. A new process leaves nothing of the old data in memory. The home-screen extension key, the logs, Hermes, the packages and whatever the bots installed stay.

The server runs on the time zone in `TZ` (UTC when unset), set in `/etc/dispatch/env` (written by the installer, or copied from `.env.prod` by every deploy), or in the dev container's `.env`; the host's clock stays on UTC. Displays, Chrome, terminals and gateways get `TZ` passed on, every Hermes config gets it as `timezone`, and routines and check-ins without a zone of their own use it.

## The model providers, SearXNG and Open-Meteo are the only services Dispatch needs

| Service | Used for |
|---|---|
| Anthropic, OpenAI, xAI, GitHub Copilot, Google, OpenRouter, DeepSeek, or a self-hosted server | Model calls from each bot's Hermes, on a subscription token or sign-in, or an API key. Dispatch itself asks the Anthropic API and the self-hosted server which models they list, and asks GitHub for the Copilot sign-in's code and token |
| SearXNG | `web_search`, when its address is set in Settings > Providers |
| GitHub | On a machine the installer set up, the newest commit of the branch it installed from, every six hours (`updates.ts`), and the installer and release when the user clicks Update. At a terminal, the installer also downloads gum, a pinned release checked against its checksum, for its full-screen questions |
| Open-Meteo | `show_weather`'s forecast cards, called by Dispatch directly (`weather.ts`) |

Hermes still fetches the models.dev registry and installs missing Python packages from PyPI when a tool needs one, and Chrome keeps its own Google traffic. Provisioning pulls Chrome, Node and Docker from their makers' apt repositories and Hermes and its Copilot plugin from GitHub at pinned commits, and each release runs `npm ci` against the npm registry. Building the speech image pulls sherpa-onnx's source from GitHub and the models from Hugging Face and GitHub, each at a pinned revision; at runtime the container has no network route out.
